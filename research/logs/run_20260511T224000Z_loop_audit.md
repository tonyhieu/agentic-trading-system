## 2. Improvement suggestions — prioritized by axis

Each item lists: **axis** (token / clarity / direction / infra), **severity**, **effort**, and **evidence** from this run.

### P0 — eliminates measurable waste in every future iteration

#### 2.1 Make `--use-cached-baseline` a flag on the canonical runner

- **Axis**: token + infra
- **Severity**: high
- **Effort**: ~30 min
- **Evidence**: This iteration wrote a 142-line per-algo `run_backtest.py` whose only purpose was to skip the re-derivation of the deterministic baseline. The agent had to spend tokens designing it, importing from `scripts.run_research_backtest`, handling the `EXECUTION_DIRS` mapping, and rebuilding aggregation. Every future agent that wants to save baseline compute will do the same.
- **Fix**: Add `--use-cached-baseline` to `scripts/run_research_backtest.py`. When set, skip the baseline-run subprocess and read `execution_algos/<baseline_dir>/results/<date>/metrics.json` directly. Fail loudly if a date is missing.
- **Knock-on**: deletes `execution_algos/<algo>/run_backtest.py` per iteration — currently each algo dir carries a copy.

#### 2.2 Pre-stage `research/CONTEXT_SNAPSHOT.md` regenerated on every DB append

- **Axis**: token + clarity
- **Severity**: high
- **Effort**: ~2 h (or reuse the SubagentStop hook)
- **Evidence**: This run still re-read OBJECTIVE.md (469 lines), config.yaml (77), program_database.json (184), NOTES.md (~growing). 79% of the iteration's tokens were cache_read on this static context. A pre-rendered ≈150-line summary would dominate the boot path and let the agent fetch full files only on demand.
- **Fix**: A SubagentStop hook (or a separate post-write hook) regenerates `research/CONTEXT_SNAPSHOT.md` with:
  - latest 3 program-DB entries summarized (`id`, status, vs_baseline_pnl_pct, trade_count, hypothesis prose first sentence)
  - the live `config.yaml` values that gate decisions (train dates, pass-gate thresholds, sigma)
  - the last 3 entries from `research/NOTES.md`
  - branch state + commit hash (cheap to compute)
- **OBJECTIVE.md change**: point the agent at `CONTEXT_SNAPSHOT.md` first; only fall back to the full DB / NOTES if it needs a specific entry's detail.

#### 2.3 Permit-set bootstrap for the researcher subagent

- **Axis**: friction / direction
- **Severity**: high (every fresh checkout hits it)
- **Effort**: 10 min
- **Evidence**: The first launch this run died at IMPLEMENT because `Write(./execution_algos/**)` and `Bash(mkdir -p *)` were not in `.claude/settings.local.json`. The agent burned 48K tokens before stopping. The orchestrator had to edit settings and relaunch.
- **Fix**: Either (a) move the canonical research-permit set into `.claude/settings.json` (project-tracked, not local) since the work is bounded to `execution_algos/**` and `research/**` by design; or (b) add a `scripts/setup_researcher_permissions.sh` that idempotently writes them to `settings.local.json` and is referenced from `docs/OBJECTIVE.md` setup section.

#### 2.4 Record `train_dates` (list) in every program-DB entry

- **Axis**: clarity / honesty
- **Severity**: high
- **Effort**: 30 min
- **Evidence**: The +140.52% headline for this run is structurally incomparable to the prior PASS scores (+14.61%, +19.85%) because those were aggregated over 3 of 12 dates. The agent flagged this in prose, but the JSON entries don't expose it as a queryable field. A future agent reading the database programmatically will see three "PASS"es with wildly different magnitudes and have to read the NOTES.md prose to understand why.
- **Fix**: Add `"train_dates": ["2026-03-08", "2026-03-09", …]` to each entry (or a `"train_window_id"` keyed to a registry). Update OBJECTIVE.md §9 schema. Add a SubagentStop validation that flags new entries comparing against prior entries with different `train_dates`.

#### 2.5 Backfill `strategy_kwargs_hash` on entries 1–6

- **Axis**: clarity
- **Severity**: medium
- **Effort**: 30 min one-time
- **Evidence**: Entries 7–9 have `strategy_kwargs_hash`; entries 1–6 do not. The schema is inconsistent. A schema validator (suggested in 2026-05-09 audit) would currently flag the older entries.
- **Fix**: One-pass migration script. Compute `sha256(canonical_json(strategy.kwargs))` at the relevant commit per entry (or set to a literal `"sha256:<old-config-at-time>"` looked up via `git show <commit-before-entry>:research/config.yaml`).

### P1 — quality and direction improvements

#### 2.6 Expose per-skip outcome attribution

- **Axis**: direction
- **Severity**: medium-high
- **Effort**: 1–2 h in the engine
- **Evidence**: This iteration's win-rate delta was only +1.5pp but PnL delta was +140%. The agent inferred (correctly) that the filter is removing high-volume low-edge trades, not high-loss losers — but it inferred. There is no infrastructure that records, per skipped child order, whether the *would-be fill* would have won or lost. Without it, every "skip-filter" iteration is calibrated indirectly.
- **Fix**: When the algorithm skips a parent order, log a counter-factual: simulate the fill at top-of-book on the same tick and tag the resulting "would-be" PnL by direction and magnitude. Write to `results/<date>/skipped_attribution.json`. The agent can then read this to choose the next filter axis (precision vs volume).

#### 2.7 Replace the consecutive-failure cap with a hypothesis-family check

- **Axis**: direction
- **Severity**: medium
- **Effort**: 2 h
- **Evidence**: The `stop_after_consecutive_failures: 3` cap has now been silently ignored or overridden in every iteration from #4 onward. This iteration sat behind two consecutive PASSes so the cap didn't bind, but the underlying issue is unchanged: the cap is theatre. Worse, it adds friction on each boot — the agent reads it, checks it, mentions it in trace prose.
- **Fix**: Either (a) raise it to a number that won't trigger casually (10) and document that overrides are explicit-only, or (b) replace with "refuse if the last 3 entries used the same `hypothesis_family`" (skip-filter / sizing / scheduling / book-state / other). Track family with a free-form field on entries.

#### 2.8 Disambiguate `close_margin_pct` in OBJECTIVE.md §4

- **Axis**: clarity
- **Severity**: low
- **Effort**: 5 min
- **Evidence**: 2026-05-09 audit flagged this; not yet fixed. The two readings (CLOSE = [3%, 5%) vs CLOSE = [3%, 7%]) produce different status calls on entries near the boundary. Every iteration that lands in that zone has to reason about it from scratch.
- **Fix**: One-line edit naming one reading and an example.

#### 2.9 Quiet the canonical runner's per-date stderr

- **Axis**: token (orchestrator side)
- **Severity**: medium
- **Effort**: requires Nautilus knob lookup
- **Evidence**: Each Nautilus backtest emits 15–20 MB of INFO-level stderr; multiply by 12 dates × 2 algos × 2 invocations on this branch alone. The orchestrator's transcript files repeatedly warn "do not read — will overflow your context." The 2026-05-09 audit suggests passing `log_level="ERROR"` to `BacktestEngineConfig`; that fix hasn't landed.
- **Fix**: Set Nautilus log level in the canonical runner. Verify in CI that a 1-day run produces <100 KB of stderr.

#### 2.10 Single source of truth for "what to compare against"

- **Axis**: clarity / direction
- **Severity**: medium
- **Effort**: 1 h
- **Evidence**: To decide PASS, the agent must read (i) the train baseline metrics from `execution_algos/<baseline>/results/<date>/metrics.json` and (ii) `pass_gate.baseline` in config. To decide refinement, it must additionally read (iii) the prior PASS algorithm's `backtest-results.json` and (iv) `refinement.targets` in config. This iteration's runner walked all of them inline. A helper would make the comparison declarative and harder to get wrong.
- **Fix**: `backtest_engine.helpers.gate_status(algo_metrics, config)` that returns one of `{"PASS", "CLOSE", "FAIL"}` plus the deltas it computed. Same shape for `refinement_status(algo, prior_pass, config)`. Saves ~40 lines of inline logic per iteration; eliminates a class of off-by-one bugs.

### P2 — pipeline-level changes

#### 2.11 Expose oracle-signal magnitude to the execution algorithm

- **Axis**: direction (biggest)
- **Severity**: high
- **Effort**: 1 day (architecture change)
- **Evidence**: Six of nine attempts to date have been book-state filters because that's the only state the execution algorithm can see. The seventh-onward have been variations on the same skip-filter axis (spread / streak / spread+streak / tighter-spread+streak). The 2026-05-09 audit called this out; the pattern is now visible across three more iterations. The research problem ("find an execution edge given a signal") is structurally smaller than the OBJECTIVE.md framing implies, because the algorithm cannot see the signal's confidence at decision time.
- **Fix**: Pass an `OracleSignalView` to the execution algorithm exposing the per-decision signal magnitude (sigma-weighted) without leaking the strategy implementation. The agent could then write filters keyed on signal quality — the natural execution edge in a noisy-oracle world.
- **Carries**: requires a corresponding update to OBJECTIVE.md §1 ("the algorithm operates with these inputs") and a worked example in the `backtest` skill.

#### 2.12 Resolve the sigma=5 ambiguity once

- **Axis**: clarity
- **Severity**: medium
- **Effort**: operator decision + 10 min edit
- **Evidence**: The 2026-05-09 NOTES.md entry "oracle sigma changed 0.5 → 5" is still open. Every iteration since then has had to recompute what the gate even means under the new regime. This iteration's caveat that the +140% headline isn't comparable to entries 1–5 traces directly back to that change.
- **Fix**: Operator decides intent. Either restore sigma=0.5 (and re-baseline) or commit a note in OBJECTIVE.md explaining that sigma=5 is the live regime and prior entries are reference-only. Either way, close the NOTES.md entry.

#### 2.13 Treat algorithm directories as ephemeral; canonicalize via git history

- **Axis**: clarity / infra
- **Severity**: low-medium
- **Effort**: 1 h
- **Evidence**: This branch (`cleanup_strategies`) deletes all prior algorithm directories. The program-DB entries reference paths that don't exist in the working tree. The agent had to know to recover prior code from git history (the operator pre-briefed this). Without the pre-brief, the agent would either re-implement from scratch (lossy) or attempt to read a missing path (error).
- **Fix**: Add `commit_sha` (the commit that introduced the algorithm) to each program-DB entry. The `snapshot` skill / `evaluate` skill / a future refinement agent then resolves code via `git show <commit_sha>:execution_algos/<id>/execution_algorithm.py` independent of the working tree. Document the convention in OBJECTIVE.md §9.

#### 2.14 Move per-algorithm `run_backtest.py` upstream

- **Axis**: infra
- **Severity**: low
- **Effort**: subsumed by 2.1
- **Evidence**: This run shipped a 142-line per-algo runner. If 2.1 lands, this directory disappears. Worth tracking until 2.1 is done.

#### 2.15 Add a `--observation` mode to the researcher prompt template

- **Axis**: friction / direction
- **Severity**: low
- **Effort**: 30 min
- **Evidence**: This run required a custom orchestrator pre-brief to suppress branch creation, snapshot push, and remote push. That's awkward — the agent definition encodes those behaviors as defaults and we had to over-ride in prose. Two more iterations on this branch would copy-paste the same prose.
- **Fix**: Add a documented flag (`OBSERVATION=1` env var or a `--observation` user-prompt prefix) that the agent prompt recognises: no `iter/` branch, no snapshot push, no remote push, but everything else (NOTES.md, DB entry, local commit) proceeds normally.
